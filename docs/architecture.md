# Architecture and engine contract

`GoatEnvironment` validates action membership and delegates every rules transition to a `RulesEngine`. `Decision` returns one acting player's `Observation` and its variable-length legal `Action` tuple. The current default engine raises `SimulatorUnavailable`; no custom Yu-Gi-Oh! rules are simulated in Python. The restricted `RestrictedOcgcoreEngine` connects a [native core](native_setup.md) to this environment for normal-monster fixture decks and three tested spells. General response decoding and complete observation coverage are still unfinished, so the default remains fail-closed.

`RulesProfile` now selects historical Side Deck sizing (0 or 15 cards) by
default, with an explicit community option for 0–15 cards. Main Decks require
at least 40 cards and have no project-imposed maximum. The experimental native
adapter has a 61-card startup test; broader large-deck behavior is unmeasured.

The observation schema has explicit visible zones, public counts, own hand and Fusion Extra Deck identities, the player's sorted initial Main Deck composition, and structured chain links. Opponent Extra Deck and unrevealed Main Deck identities are withheld. Field monsters record visible attack or defense position and, while face-up, current ATK, DEF, and counters. Face-down cards have no dynamic stats in either player view. The native adapter records bounded public turn, phase, attack, Damage Step, and chain events. It also records public `MSG_CONFIRM_DECKTOP` reveals, the current public `MSG_FIELD_DISABLED` zone mask, and opponent field cards seen face-up immediately before a public face-down position change; move, set, swap, and set-card shuffle events invalidate the latter memory. `MSG_CONFIRM_CARDS` messages are stored only for their addressed recipient, as sorted card multisets without native sequence numbers; the viewer cannot see the other recipient's message at that decision. It tracks opponent hand identities only when a public Graveyard or face-up field card moves to hand, as an unordered multiset. Private draws add no identity, and an ambiguous move out of the hand clears this memory. It has no unrevealed opponent hand identities or deck order. Other reveal messages and richer history need an audit. Schema shape alone cannot prove the native adapter redacts data. The native adapter must use the engine's player-scoped queries, hide facedown cards where appropriate, and test identical visible states with different hidden cards. Action IDs are local to a decision and must map to the exact native response payload; effects with targets or multiple choices may take several decisions. Flip Summons are distinguished from face-up position changes in the public action API. Two-zone field prompts use canonical unordered pairs of zone triples encoded as the core's six response bytes. Prompts needing more than 2,048 combinations still fail explicitly; a staged-action interface is needed to support them at scale.

## Next adapter implementation

1. Pin ocgcore, card database, and script revisions with checksums. Build the native core outside this repository or as a separately licensed optional package.
2. Start duels with `DUEL_MODE_GOAT`, 8000 LP, five starting cards, one draw per turn, and seeded PRNG. Parse `.ydk` and verify the April 2005 banlist and card pool before duel creation.
3. Parse every core request message into legal actions, including card/effect selection, chained responses, targets, positions, tribute choices, attacks, and phase transitions. Map each selected action back to exact response bytes; reject overflow or unsupported messages explicitly.
4. Construct player-scoped observations from native queries. Test hidden opponent hands, deck order, facedown identities, and privately revealed information. Capture public history and known-card memory only through observed events.
5. Run a complete duel with two random agents; add historical ruling fixtures. Then add multiworker runs and measured benchmarks.

Do not use `ygoenv`'s current EDOPro binary as a GOAT engine: its source currently selects MR5. The direct `ctypes` probe reaches real native decisions without a fixed option-list size, so it is the current M1 adapter direction. Its response protocol and visibility boundary are only partially implemented. The interface avoids coupling downstream agent and replay code to this choice.

Trajectory JSON schema v17 stores the visible observation, full legal action list, chosen action, acting player and phase (inside the observation), deck identifiers, ruleset, source, optional skill metadata, and result. It retains monster orientation and structured chain links from v2, the rules profile, deck hashes, and loaded native-asset hashes from v3, and the latest 64 observed public turn, phase, attack, Damage Step, and chain events from v4. Version 5 adds opponent field-card identities known through a public face-up-to-facedown position change; version 6 associates those identities with controller, zone, and slot. Version 7 populates a narrow public Scapegoat summon restriction from native player-hint add/remove events. Version 8 adds public Deck-top reveals and distinguishes Flip Summons from face-up position changes. Version 9 adds active disabled field zones from a public native message. Version 10 adds recipient-scoped private card reveals. Version 11 adds the player's initial Main Deck as a sorted multiset. Version 12 adds visible current monster ATK, DEF, and counters. Version 13 removes native Deck and Extra Deck slot numbers from action parameters and canonicalizes ordinary Deck-search choice order by visible values. Version 14 retains recipient-addressed reveals of face-down opponent field cards as known identities tied to field slots; the current field view remains face-down. Version 15 carries prior known identity across face-down field-to-field control changes. Version 16 retains a former controller’s knowledge when its own face-down card changes control, including native swap messages; raw IDs are used only when both the former and new controllers can legally know the card. Version 17 adds an unordered, conservative multiset of opponent hand cards observed returning from the public Graveyard or face-up field; a private draw adds no identity, and an ambiguous hand exit clears memory. The reader accepts v1–v17 trajectories; the verifier ignores fields added later when checking older recordings and maps older position actions at Flip Summon decisions. Pre-v13 recordings with Deck-search choices, pre-v14 recordings with addressed face-down field reveals, and pre-v15 recordings with face-down control returns pre-v16 recordings with transferred set cards, and pre-v17 recordings with public hand returns may require re-recording for exact action and observation comparison; other earlier fingerprinted recordings remain verifiable. No native full-state snapshot is stored. The optional [PyTorch policy](ml.md) maps player-visible decisions to variable-length action logits independently of the simulator. The behavioral cloning command verifies trajectories before fitting; other training algorithms can use the same decision boundary.

`goat_ai.replay.verify_trajectory` reconstructs a duel from its seed and
decklists, compares each player-visible observation and complete legal-action
set with the recording, applies the selected action, and checks the result.
Schemas v3–v17 verify deck contents and native asset fingerprints as well as the
recorded path. Callers must retain the original deck files and native assets;
the recording stores hashes, not copies. Older v1/v2 recordings can still be
replayed but lack these content checks.

`goat_ai.evaluation.run_tournament` depends only on the `RulesEngine` and agent interfaces. It runs each seed and matchup with both seat assignments and records wins, losses, draws, decisions, and a Wilson interval for decisive wins. The native CLI adds deck and asset fingerprints. This keeps evaluation separate from policy implementation and makes later checkpoint opponents possible without changing the duel engine.

`run_tournament_parallel` executes the same schedule in spawned processes and
returns results in schedule order. It requires pickleable top-level agent and
engine factories, such as a class or `functools.partial`; spawning avoids
inheriting live native duel state. The native evaluation CLI accepts
`--workers`. The engine and public agent interfaces are unchanged, so future
network inference can use the same schedule with a suitable worker factory.
